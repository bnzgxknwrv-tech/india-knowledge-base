# INDIA SUCCESSOR BOOT PROTOCOL — LIGHT VERSION

Status: BINDING for INDIA10+ until explicitly superseded.
Effective: 2026-08-23.
Purpose: preserve useful travel knowledge without turning this personal travel repository into a compliance system.

## The rule in one sentence
Read the current state, protect Mark's existing decisions, read the meaningful recent delta relevant to the task, and then get on with the travel work.

## 1. Normal start
A new IndiaN reads, in this order:
1. `README.md`;
2. `governance/CURRENT_STATE.md`;
3. `runs/active/INDIAZILVER-ENTITY-ID-PROXIMITY-BACKFILL-001/PROTECTED_CANON_BASELINE.csv`;
4. the current task/output files relevant to Mark's request;
5. recent PR #23 exchanges not yet handled when they materially affect the task.

This is normally enough. There is no routine requirement to reread the whole repository, compute byte percentages or recertify old unchanged files.

## 2. Baseline + delta is a convenience, not a ceremony
The INDIA9 baseline/audit files remain useful evidence that older branch knowledge was inspected and imported or archived. Use them when provenance matters or when something appears missing.

For normal work, read the meaningful changes since the current-state page / last known handoff that are relevant to the task. If a conflict or unexplained gap appears, widen the read until it is understood. Full-repository bootstrap is an exceptional recovery option, not a default gate.

## 3. `AL BESLIST?`
Before presenting a location, cluster, hotel, sleep base or route choice as new, check protected canon/current decisions first.

If Mark has already decided it, do not ask him to decide it again. Report only a real new delta that could matter.

## 4. Mark decisions and permanent IDs
Existing Mark A/B/C choices, locks and permanent IDs are protected against silent mutation. A new explicit Mark decision may supersede an older one; when it does, update the durable canon clearly instead of keeping competing current truths.

## 5. Worker output is not automatically central truth
A worker branch saying `COMPLETE` means the worker finished its assignment. It does not automatically mean the result has been adopted centrally or is ready for route use. Check integration/adoption before relying on it as final state.

No separate central-integration bureaucracy is required when this is obvious from the current state and Git history.

## 6. Fresh travel facts
Visa rules, access/opening, timetables, availability, prices, weather and similar facts change. Recheck them when they are actually about to influence advice, routing or booking.

Do not block unrelated work because some unused live fact is old.

## 7. CCI collaboration
Use `governance/CCI_COLLABORATION_PROTOCOL.md`.

For a material architecture/central-integration change, one CCI sanity review is normally enough. PR #23 is the review record. No duplicate review receipts are needed.

Polling is light: check PR #23 before a major new build and immediately before a central write.

## 8. Keep one current-state page useful
`governance/CURRENT_STATE.md` is the human-readable current pointer. Update it when a change would materially affect how the next INDIA session continues: a Mark decision, important task completion/blocker, central adoption, current route/base state or other real handoff fact.

Do not update it for every trivial commit.

## 9. Do what is safely doable, but do not manufacture work
If INDIA can safely finish a useful step now, finish it rather than hand it back to Mark as avoidable homework. But no-deferral does not mean inventing extra audits, validators or process tasks just to make a status look more complete.

## 10. Good-enough threshold
IndiaN may say `READY_TO_CONTINUE` when it has enough current context to act responsibly: current state + protected canon + relevant current files + material recent relay delta.

If those sources disagree, resolve the disagreement first. Otherwise continue. No `100% knowledge` percentage is required.

## Historical note
The heavier task-008 baseline/gate architecture and INDIA9 audit remain in Git history and archive as provenance. They solved a real one-time knowledge-loss problem. Their detailed percentage gates, blob taxonomies and certification mechanics are intentionally not standing daily requirements anymore.
