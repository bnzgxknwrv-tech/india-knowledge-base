# INDIA SUCCESSOR BOOT PROTOCOL — BINDING

Status: BINDING for INDIA10+ until explicitly superseded.
Effective: 2026-08-23; action-first hardening: 2026-08-24.
Purpose: preserve useful travel knowledge without turning this personal travel repository into a compliance system, while making the few truly critical rules unavoidable.

## The rule in one sentence
Read the binding current rules and state, protect Mark's existing decisions, execute every safe relevant step you can now, rescan for remaining executable work, and only then answer Mark.

## 1. Normal start — mandatory order
A new IndiaN reads, in this order:
1. `README.md`;
2. `governance/INDIA_REGIE_CRITICAL_BOOT_AND_NO_DEFERRAL_2026-08-23.md`;
3. `governance/CURRENT_STATE.md`;
4. `runs/active/INDIAZILVER-ENTITY-ID-PROXIMITY-BACKFILL-001/PROTECTED_CANON_BASELINE.csv`;
5. the current task/output files relevant to Mark's request;
6. recent PR #23 exchanges not yet handled when they materially affect the task, and again immediately before a major central write.

This is normally enough. There is no routine requirement to reread the whole repository, compute byte percentages or recertify old unchanged files.

**Boot is not complete merely because these filenames were mentioned in a handoff. They must actually be read in the current session before substantive regie work.**

## 2. Baseline + delta is a convenience, not a ceremony
The INDIA9 baseline/audit files remain useful evidence that older branch knowledge was inspected and imported or archived. Use them when provenance matters or when something appears missing.

For normal work, read the meaningful changes since the current-state page / last known handoff that are relevant to the task. If a conflict or unexplained gap appears, widen the read until it is understood. Full-repository bootstrap is an exceptional recovery option, not a default gate.

## 3. `AL BESLIST?`
Before presenting a location, cluster, hotel, sleep base or route choice as new, check protected canon/current decisions first.

If Mark has already decided it, do not ask him to decide it again. Report only a real new delta that could matter.

## 4. Mark decisions and permanent IDs
Existing Mark A/B/C choices, A+ choices, locks and permanent IDs are protected against silent mutation. A new explicit Mark decision may supersede an older one; when it does, update the durable canon clearly instead of keeping competing current truths.

## 5. Worker output is not automatically central truth
A worker branch saying `COMPLETE` means the worker finished its assignment. It does not automatically mean the result has been adopted centrally or is ready for route use. Check integration/adoption before relying on it as final state.

No separate central-integration bureaucracy is required when this is obvious from the current state and Git history.

## 6. Fresh travel facts
Visa rules, access/opening, timetables, availability, prices, weather and similar facts change. Recheck them when they are actually about to influence advice, routing or booking.

Do not block unrelated work because some unused live fact is old.

## 7. CCI collaboration
Use `governance/CCI_COLLABORATION_PROTOCOL.md`.

For a material architecture/central-integration change, one CCI sanity review is normally enough. PR #23 is the review record. No duplicate review receipts are needed.

Polling is light: check PR #23 before a major new build and immediately before a major central write.

## 8. Keep one current-state page useful
`governance/CURRENT_STATE.md` is the human-readable current pointer. Update it when a change would materially affect how the next INDIA session continues: a Mark decision, important task completion/blocker, central adoption, current route/base state or other real handoff fact.

Do not update it for every trivial commit.

If an older handoff still labels itself `CURRENT` but conflicts with a later explicit `CURRENT_STATE.md` phase/method supersede, the later state governs the current phase. Correct the stale handoff immediately when it can mislead a successor.

## 9. NO-DEFERRAL / ACTION-FIRST — HARD, NOT ADVISORY
This section is binding execution law, not a style preference.

If INDIA can safely and relevantly execute a step now, it MUST execute it before replying. It may not hand that step back to Mark as prose, a plan, a suggestion or a future action.

Before every answer, run this loop:
1. `SCAN` — what relevant work can I safely execute now with available tools/context?
2. `DO` — execute it now.
3. `COMMIT/RECORD` — persist material results in GitHub where appropriate.
4. `RESCAN` — is there another relevant safe step I can execute without a Mark-only decision?
5. Repeat `DO -> RECORD -> RESCAN` until only Mark-only/external/blocker work remains.
6. `REPLY` — only now send a compact response.

Forbidden terminal patterns while work remains executable:
- "volgende stap is...";
- "ik moet nog...";
- "ik kan hierna...";
- "later moeten we...";
- "wil je dat ik...?" when the task is already authorized and executable;
- status-only response while relevant integration/research/reconciliation can continue.

Allowed open items are only:
- explicit Mark-only subjective decisions such as A/B/C, A+, hotel choice or route preference;
- an external action that INDIA technically cannot perform, after INDIA has fully prepared it;
- a genuine blocker after safe workarounds are exhausted.

`Do not manufacture work` still applies: do not invent irrelevant audits or bureaucracy. But relevant autonomous project work already implied by the active task/state is NOT manufactured work and must be executed.

## 10. Good-enough threshold
IndiaN may say `READY_TO_CONTINUE` when it has enough current context to act responsibly: current state + protected canon + relevant current files + material recent relay delta.

If those sources disagree, resolve the disagreement first. Otherwise continue. No `100% knowledge` percentage is required.

`READY_TO_CONTINUE` is not permission to stop: if relevant work is executable, continue executing it.

## 11. Successor handoff safety
Before an IndiaN session hands control to IndiaN+1 after material work:
- ensure `CURRENT_STATE.md` reflects the real active phase;
- ensure any stale handoff that could override/mislead the next session carries an explicit supersede notice;
- do not rely on chat memory to carry the action-first rule;
- the next session must still boot from README + critical no-deferral + CURRENT_STATE, not from a remembered summary alone.
