# R31 — A "TWO KEYS" GATE IS ONLY FAIL-CLOSED IF THE SECOND KEY HAS ITS OWN VALIDATOR
Failure exposed 2026-08-30, immediately after R30/V8 landed (PR #28 merged to central at `366328029b6bb7b7b0ab36f6683e7086bf4ff33d`): an independent ChatGPT Work audit (PR #23 comment `5470210435`) found that V8's own "independent CHECK is a second key" design was itself not mechanically enforced. Specifically: the canonical START/CHECK protocol file was not in the mandatory manifest read set; there was no validator for a `boot_checks/` artifact at all; the START protocol's own step 6 and the CHECK's stale-receipt test described the receipt/HEAD relationship inconsistently with each other and with what the validator actually checked; and session/nonce values were accepted as any non-empty string with no format or freshness check. A mechanically-PASSing first key (the receipt) could therefore still reach something functionally indistinguishable from authorization without a real, bound, fail-closed second key ever running.

This is a direct generalization of R30 one layer up: R30 was about a mandatory *file set* drifting out of sync; R31 is about a mandatory *second validator* being designed in prose but never actually built, so the "two keys" property was aspirational rather than enforced.

Hard correction:
1. if a protocol document declares that a second, independent verification step is required before some authorization may be granted, that declaration is not complete until (a) the document itself is in the mandatory read set a validator checks for, and (b) a SEPARATE script mechanically validates the second artifact against the first, with its own fail-closed checks — not merely a written expectation that a future session will do the right thing;
2. the two validators must agree on ONE canonical description of any shared mechanism (here: the commit-chain HEAD/receipt shape) — restated inconsistently in multiple files is itself a defect even if each restatement is individually well-intentioned;
3. any identity/freshness field accepted from the command line or written self-report (session labels, nonces, timestamps) must be format-validated and, where the underlying git/commit evidence allows it, cross-checked against that independent evidence — not merely checked for non-emptiness or internal self-consistency;
4. exactly one script should be the sole place a system prints its final "authorization granted" string, composing the sub-validators rather than duplicating their logic, so there is never more than one place that claim could be made incorrectly.

General principle:
**Declaring a second key in prose does not create a second key. A "two keys" authorization design is only as fail-closed as its least-enforced key — build and test the second validator with the same rigor as the first, in the same change, not as a documented intention for later.**

# R32 — A FIELD BEING "NOT EMPTY" IS NOT THE SAME AS A FIELD BEING SUBSTANTIVE, AND A CHECKER GRADING ITS OWN TEXT IS NOT A SECOND OPINION
Failure exposed 2026-08-30, immediately after R31's independent-CHECK validator landed: a fresh independent Work re-audit (PR #23 comment `5470939825`) demonstrated, with a concrete local/unpushed adversarial test, that `validate_independent_check.py` only required each challenge's `answer`/`evidence` fields to be non-empty. Replacing all eight `answer` and all eight `evidence` fields with the literal string `"x"` — leaving topics/questions/verdicts and the valid C->R->K commit shape intact — still produced exit 0 and `CONTENT_AUTHORIZATION: GRANTED`. The deeper defect this exposed was not merely a missing length check: the CHECK artifact let one party (the checker) author BOTH the "answer" being tested AND its own grading of that answer as a single self-declared field, so a checker could satisfy the schema with eight topic labels and self-issued PASS verdicts while the actual boot session's knowledge was never demonstrated at all.

This is a direct generalization of R31 one layer deeper: R31 established that the second key needed ITS OWN validator; R32 establishes that the second validator's checks must bind to content that did not originate from the party being validated, not merely to non-empty strings that party wrote itself.

Hard correction:
1. "field is present" and "field is not empty" are necessary but never sufficient checks on content meant to demonstrate substantive knowledge — a validator protecting against a self-interested or careless author must also reject minimum-length, word-count, and known-placeholder/filler patterns (`"x"`, `"n/a"`, `"tbd"`, repeated-character strings, etc.) as an explicit floor;
2. wherever a design calls for "the checker verifies the answer," the schema must structurally separate the thing being graded (the answer) from the grade itself (the checker's evidence and verdict) into different fields authored by different roles — a single self-authored field cannot be both the content under test and the judgment about that content;
3. where a field claims to cite source evidence, the validator should mechanically confirm the citation names a real, checkable path in the mandatory source set (or the artifact under review) rather than accepting free-text prose that merely asserts a conclusion;
4. this repository's file/git architecture has no live channel for a second session to interrogate a first session in real time — the practical, honestly-achievable approximation is a human-relayed challenge/response round trip (Mark copies the CHECK session's question to the START session and relays the exact reply back), recorded as a separate `start_session_answer` field — see `governance/INDIA14_START_AND_INDEPENDENT_CHECK.md` section 2.4a. This is NOT cryptographic proof that the relay was unmodified or that the two sessions are genuinely distinct reasoning processes; it is a stronger floor than a checker self-authoring both sides, not a complete solution, and must be documented as such rather than overclaimed.

General principle:
**A validator that only checks "not empty" invites exactly the minimum-effort content that satisfies it and nothing more. When one party can author both the claim and the grade of that claim in a single field, the "second key" collapses back into the first one wearing a different filename — the fix is structurally separating who authors the content under test from who grades it, plus a content floor even the honor-system relay cannot fully replace.**


# R33 — A CHECKPOINT'S "NEXT STEP" MUST NEVER DESCRIBE THE ACTION ITS OWN WRITER IS MID-WAY THROUGH
Failure exposed 2026-08-30, three separate times across the R30-R32 repair sequence (V8 Work-audit MUST_FIX repair, PR #23 comment `5470740209`; V8 fresh re-audit MUST_FIX repair, comment `5471479783`; V8 final practical sanity check, `WORK_RESULT`): each repair round updated `governance/SUCCESSOR_SAFE_STATE.md`'s `NEXT_AUTOMATIC_STEP` field to say "post the CCI_RESULT comment for this round" — but by the time any successor session actually reads that field, the comment described has, without exception, already been posted (the session writing the checkpoint is either about to post it or has just posted it in the same work session). Every subsequent independent Work audit correctly flagged this as a stale-redo instruction, making it the single most repeated defect class of this entire repair sequence — one narrow bug rediscovered three times because the fix pattern used to close it each time reintroduced the same shape of bug.

Root cause: a checkpoint field describing "what happens next" was being written from the perspective of the moment of writing (when the described action is imminent or just-completed and therefore true) rather than from the perspective of the moment of reading (when a fresh successor session opens the file and the described action is already history). These two perspectives are not interchangeable, and no amount of re-fixing the specific comment ID or wording closes the class — only changing what kind of statement is allowed in that field does.

Hard correction:
1. `NEXT_AUTOMATIC_STEP` (and any field with a similar "what to do next" role in any governance file) must never describe posting, committing, or pushing an artifact that the same commit/round is itself producing — if an action is being completed as part of writing the checkpoint, it belongs in `LAST_COMPLETED`, never in `NEXT_AUTOMATIC_STEP`;
2. before finalizing any checkpoint update, the writer must explicitly ask "will this sentence still be true in the future tense for a reader who opens this file after my own commit exists?" — if the honest answer requires assuming the reader is looking at a moment before this commit is even pushed, the sentence is mis-scoped and belongs in LAST_COMPLETED instead;
3. a `NEXT_AUTOMATIC_STEP` that names a decision only Mark can make (as opposed to a mechanical action a session can perform) should say so explicitly and stop there, rather than also listing a mechanical sub-step that this same commit is completing.

General principle:
**A "next step" field is read in the future by someone who was not present when it was written. If it describes an action synchronous with its own writing, it is already false the moment it is committed — write every forward-looking field as if the ink is already dry on everything this commit did.**

# R34 — A UNIFORM SECOND KEY MUST BE PROPORTIONAL TO ACTUAL RISK, NOT UNIFORMLY MAXIMAL, OR IT STOPS BEING USED CORRECTLY
Problem raised directly by Mark, 2026-09-01, after INDIA12→13→14→15 forced four fresh sessions in rapid succession (ChatGPT's own session limits, not a project choice): the R31/R32 full independent CHECK — a genuinely separate ChatGPT session, all eight mandatory topics, and a manual two-way relay where Mark personally copies the CHECK session's questions to the START session and relays the eight verbatim answers back — was running in full on **every single** fresh session, including routine continuations where nothing about the project's governing knowledge had changed since the last time a full CHECK passed. This cost Mark real manual relay time and a whole second ChatGPT conversation every time, disproportionate to the actual risk being guarded against on a boot where the governance file set is provably unchanged.

This is a different failure shape from R30-R32. R30 was a boot generation shipped partially applied; R31 was a declared second key with no real validator; R32 was a validator whose floor was too weak (non-empty was mistaken for substantive). R34 is none of those — the full CHECK mechanism was, by this point, genuinely fail-closed and doing its job. The problem was that a control correctly sized for "did the governance rules just change" was being applied unconditionally to "is this an ordinary continuation," making the expensive case (Mark's time) the common case instead of the rare one — which in practice pushes toward skipping or resenting the gate rather than a change to the actual risk it guards against.

Fix, approved directly by Mark in the live session ("Ja, herstructureer zo"): a two-tier CHECK.
1. **Part 1 (mechanical boot + receipt) is completely unchanged and stays mandatory for every single fresh session, unweakened.** It is what directly fixes the real 2026-08-30 incident this whole boot architecture exists to prevent (a session skipping the actual boot and violating the already-redundant train-first rule) and it is already cheap — no second session, no manual relay. Nothing about R34 touches Part 1.
2. **Part 2 (the independent CHECK) becomes proportional to whether the governance file set actually changed.** A FULL check (unchanged R31/R32 mechanics) is required exactly when: no prior PASSing FULL check exists whose reviewed receipt's `central_required` blob-SHA set exactly matches the current session's own; Mark explicitly asks for one anyway; or a prior LIGHT spot-check in the current state FAILed and hasn't since been superseded by a passing FULL. Otherwise a LIGHT spot-check suffices: the SAME session self-answers 2-3 topics chosen deterministically from its own `boot_head_final`, with no second session and no relay.
3. **Tier eligibility is derived live from real git blob SHAs, never from a hand-maintained pointer or version field.** This is a direct application of the R30 lesson one layer up: R30 showed that a manually-tracked "which generation is this file on" pointer rots the moment one owner file is edited without the others. A hand-maintained "has the governance set changed since the last full check" flag would rot the exact same way. Instead, `validate_independent_check.py` walks `governance/boot_checks/` for the most recent PASSing FULL check, reads its receipt's `boot_head_final`, computes the real blob SHA of every `central_required` path at that commit, and compares that map byte-for-byte against the same map at the current session's `boot_head_final`. There is nothing to remember to update; the answer is always recomputed from what is actually true in git.
4. **LIGHT never silently substitutes for a required FULL check.** A LIGHT attempt that fails the blob-SHA eligibility test fails closed with an explicit "a FULL CHECK is required for this boot" error, exactly like every other fail-closed check in this architecture — it does not degrade further, and a spot-check FAIL always escalates to demanding a full check next rather than permitting a retry at the same lightness.
5. **LIGHT keeps the SAME anti-triviality floor as FULL** (`is_trivial_text`, minimum length/word counts, mandatory-source-path citation) on every individual answer — the tradeoff is in HOW MANY topics and WHO authors them (self vs. a genuinely separate session), never in how easy one answer is to fake.
6. **The honest limit must be stated plainly, not overclaimed.** LIGHT drops exactly the thing R31/R32 built FULL for: a genuinely separate session authoring the question and grading a relayed answer. In LIGHT mode the same session authors the question, the answer, and its own grade of that answer. This is a deliberate, Mark-approved cost/rigor tradeoff for the routine case where the governance file set provably has not changed — documented as weaker, never presented as equally strong. See `governance/INDIA14_START_AND_INDEPENDENT_CHECK.md` §2.0/§2.8/§2.8.7 and `governance/boot_checks/README.md`.

Scope note: tier eligibility is deliberately scoped to `central_required` ONLY, never `cci_required` (pinned/immutable, cannot change) or `active_cluster_required` (changes with every ordinary piece of travel-content progress). Tying tiering to either of those would force a FULL check on routine cluster work and defeat the entire point — the proportionality is specifically about whether the GOVERNING rules changed, not whether the trip plan advanced.

Practical consequence worth stating explicitly: the commit that ships R34 itself changes several `central_required` files (this file, `INDIA_MASTER_BOOT.md`, `INDIA14_START_AND_INDEPENDENT_CHECK.md`, `CURRENT_STATE.md`, `SUCCESSOR_SAFE_STATE.md`). That means the FIRST session to boot after this commit lands cannot be LIGHT-eligible — no prior FULL check's blob-SHA map can match the new content yet — and must run a FULL check. This is intentional, not a gap: a change to the governing rules themselves must be verified once against the new rules before any session may treat the cheaper path as available, and that first FULL check becomes the new baseline every subsequent LIGHT-eligible session compares against.

General principle:
**A second key sized correctly for the rare case (the governing rules just changed) but applied uniformly to the common case (an ordinary continuation) is not more rigorous than a correctly-sized key — it is a control that will be resented, and in practice a control people are pushed to work around is weaker than one they use willingly. Proportionality is not a weakening of a fail-closed gate; a gate that fails closed exactly as hard when it actually matters, and steps aside cleanly and honestly when it provably does not, is the more sustainable design. The fix is never a hand-maintained "has it changed" flag (R30 already showed that rots) — it is deriving the answer live from the same git evidence the rest of this architecture already trusts.**


# R35 — A SESSION'S OWN LATE-TURN "FINAL" CHECKPOINT CAN SILENTLY REVERT ITS OWN RECENT CORRECTION; INCREMENTAL WRITES MUST NOT DEPEND ON THE LAST MESSAGE BEING RELIABLE
Failure exposed 2026-09-01/02: within a single live INDIA15 conversation, the session correctly self-corrected mid-conversation — it found, verified against the actual pinned Delhi Lonely-Planet-layer file (`runs/active/INDIA10-CLUSTER-COVERAGE-REAUDIT-001/DELHI_SPARE_DAY_LP_TOPX_LAYER_2026-08-31.md`, status `PREPARED / ... / NO NEW GRADES`, 32 `[OPEN / NOT GRADED]` items never triaged by Mark), that its own earlier claim of having reached the `OPTIONAL_WORLD_SURVIVAL` frontier was premature, and stated it would build a cluster-by-cluster Layer-A/LP status matrix instead. Later in the SAME session, near its own context limit, Mark sent a generic "write everything down now, this is your last message" closing prompt. The resulting commit (`eab5aff`, "crash-safe final checkpoint before context limit") did NOT incorporate that correction — it reverted to the older, already-superseded claim that Delhi's traveler layer and the optional-world comparison were complete, and explicitly filed the session's own recent, verified correction under `HALF_FINISHED_CHAT_WORK = NIET_MEER_GELDIG / DO_NOT_RESUME`, discarding a genuine finding as if it had been idle chat noise.

Root cause: a single large "write it all down now" prompt, issued once near the end of a long turn, asks a session that may already be degraded/compressed to reconstruct everything from a wide span of its own context in one shot. Under that pressure it is easy to reach for the safest-looking anchor — the last thing already committed to GitHub — rather than genuinely reconciling against everything reasoned since. The result looks like a proper crash-safe checkpoint (it has the right shape, the right section headers, a plausible "half-finished work" classification) while actually being WRONG on a specific, checkable point. A single end-of-turn prompt is therefore not a substitute for genuine incremental capture, no matter how well that prompt is worded — it is a last-resort backstop for whatever wasn't captured earlier, not the primary save mechanism.

This directly generalizes rule 21/22 of `governance/INDIA_BEHAVIORAL_EXECUTION_CONTRACT.md` (checkpoint durable state after every material result, do not defer to the end): those rules were already correctly stated, but stating them once is not the same as a session reliably following them under its own end-of-context pressure, and no existing rule told a session what to do when its own late "final" checkpoint would contradict something it itself concluded earlier in the same turn.

Hard correction:
1. treat any single "this is my last message, save everything" prompt as a backstop, never the primary mechanism — the real fix is writing durable state after each material finding/reconciliation/correction AS IT HAPPENS, per rule 21/22, so there is nothing large left to reconstruct under pressure at the end;
2. when a session does write a late/final/crash-safe checkpoint, it must explicitly diff its own conclusion against what is CURRENTLY committed in the controlling files before writing — if they disagree, the checkpoint must say so explicitly (which one is correct, why, and that the other is being superseded) rather than silently picking the already-committed version as the default;
3. a finding produced and verified against real pinned source files earlier in the SAME session is not "half-finished chat work" merely because the session did not get around to committing it before being asked to wrap up — evidence-backed conclusions and genuinely abandoned/incomplete threads are different things and must not be classified identically;
4. Mark independently re-verifying a session's own crash-safe claim against the actual underlying source file (as was done here, catching this exact reversion) remains a necessary check, not a redundant one — a checkpoint's internal shape being correct is not evidence that its content is correct.

General principle:
**A session that only saves at the very end is betting its entire turn's work on the reliability of its own last message, at exactly the moment — near its own context limit — when that message is least reliable. The fix is never a better final prompt; it is not needing one, because nothing material was left unsaved by the time it arrives.**


# R36 — MECHANICALLY PROVING A FILE WAS READ IS NOT THE SAME GUARANTEE AS THAT FILE'S CONTENT BEING BEHAVIORALLY COMPILED INTO ONE CONSISTENT WORKING SET
Failure class confirmed by a CCI review round, 2026-09-02 (`CCI_RESULT — INDIA16 ACTIVE MEMORY CONSENSUS`, PR #23 comment `5501775926`), against a real, reproduced INDIA15 incident: a fresh session can pass every mechanical boot-receipt check in `validate_successor_boot.py` — every mandatory file's blob SHA pinned, full byte-range read coverage proven, verbatim proof-of-read quotes verified — while still acting on stale or mutually contradictory frontier information drawn from those same files. `READ_COMPLETE` (proven by the receipt) and `ACTIVE_MEMORY_COMPILED` (the mandatory sources actually reconciled into one consistent working set before answering) are different guarantees, and the boot architecture up to R35 only mechanically proved the first one.

Concrete incidents that exposed this in the live INDIA15 conversation:
1. **Letter-grade confusion.** INDIA15 labeled Delhi traveler corridors/presentation options `A`, `B`, `C`, `D`, `E`... — reusing the letters reserved exclusively for Mark's subjective `A+`/`A`/`A*`/`B`/`C` travel grades — even though the reservation was implicit in every mandatory file it had "read." Fixed by the explicit `LOCKED_BY_MARK` rule at `decisions/PRESENTATION_GRADE_LETTERS_RESERVED_MARK_RULE_2026-09-02.md` and now also codified as an executable veto (`INDIA_BEHAVIORAL_EXECUTION_CONTRACT.md` §26).
2. **Carried-forward Delhi `[B]` grades shown without provenance.** Existing, already-`LOCKED_BY_MARK` Delhi grades were re-displayed during a new presentation pass without immediately making clear they were prior decisions, not a fresh INDIA valuation — creating exactly the ambiguity `AL BESLIST?` (§3 of the behavioral contract) exists to prevent, despite that section having been "read."
3. **Stale `OPTIONAL_WORLD_SURVIVAL` frontier.** Mandatory/current sources still asserted the old `DURATION_CLOSED x6 -> OPTIONAL_WORLD_SURVIVAL` process state after newer source reconciliation (`RESEARCH_VS_TRIAGE_VS_DURATION`) had already disproved it — later-repaired traveler-layer research existed for Agra, Bodh Gaya and Tiruvannamalai that Mark had not yet triaged, meaning those worlds could not honestly be called `DURATION_CLOSED` yet. A session booting during the stale window would mechanically read `CURRENT_STATE.md` and still land on the wrong frontier if it trusted a differently-worded router/pointer file over the more authoritative source, because nothing checked that the pointer and the authority actually agreed.
4. **Missing `active_cluster` cross-check (the concrete validator bug).** `validate_successor_boot.py` checked a receipt's `active_cluster` field only against `BOOT_MANIFEST_V8.json`'s OWN `active_cluster` value — never against `CURRENT_STATE.md`'s `manifest_active_cluster:` line, the more authoritative, human-legible source of truth. This meant a session that correctly derived the frontier from `CURRENT_STATE.md` could mechanically FAIL the receipt validator if the manifest lagged, while a session that echoed a stale manifest value straight back would mechanically PASS — the validator was structurally incapable of catching the exact class of drift it needed to catch.

Root cause: the boot architecture through R35 hardened WHETHER mandatory files were read (byte coverage, blob pinning, verbatim quotes) but never asked WHETHER the files, once read, actually agreed with each other, and never cross-checked the one validator field (`active_cluster`) that most directly encodes "where is the project right now" against more than one of its own sources.

INDIA15+CCI consensus fix (2026-09-02, proportionality-scoped per R30-R35 — reuse existing machinery, no new artifact type):
1. `governance/INDIA_ACTIVE_MEMORY_COMPILATION_GATE.md` added as `central_required` #4 in `BOOT_MANIFEST_V8.json` and as mandatory boot-list read #4 in `INDIA_MASTER_BOOT.md` — an explicit pre-answer step requiring the mandatory current-state/decisions/knowledge-map sources to be actively reconciled, not merely individually read.
2. `INDIA_BEHAVIORAL_EXECUTION_CONTRACT.md` §25 (PRE-ANSWER CONTRADICTION VETO) and §26 (GRADE-LETTER RESERVATION VETO) materialize both incidents above as executable pre-answer checks, additive to the existing 22-point (now 24-point) veto.
3. `validate_successor_boot.py` now parses `CURRENT_STATE.md`'s `manifest_active_cluster:` value and FAILs closed if it does not exactly string-equal the manifest's own `active_cluster` field — purely structural, no semantic judgment about which value is "right," only that the two currently-designated authorities agree.
4. `validate_independent_check.py` extends the `FRONTIER_CONTRADICTION_CHECK` topic (new in `check_required_challenge_topics`) to require `checker_evidence` citing all three of `CURRENT_STATE.md`, `CURRENT_DECISIONS_MASTER.md` and `INDIA_CURRENT_KNOWLEDGE_MAP.md` by name, instead of the usual single-source citation floor.
5. **Explicitly rejected by INDIA15's own design choice, respected here:** no new `compiled_working_set` receipt field, no second `ACTIVE_MEMORY_READY` signal, no new parallel compilation JSON artifact. The existing manifest/validator/CHECK/CONTENT_AUTHORIZATION machinery was extended rather than duplicated, matching the proportionality discipline R30-R35 already established.

Honest residual limit (state plainly, do not overclaim): none of the four mechanical additions above can verify that a session's PROSE actually reflects the reconciliation it claims — `validate_independent_check.py` verifies that `FRONTIER_CONTRADICTION_CHECK` evidence cites three real mandatory files by path, not that their content was genuinely, correctly reconciled in the session's head before it answered. That residual judgment still rests with the CHECK session's own semantic grading and, ultimately, Mark's own scrutiny — exactly the same honest limit already stated for every other mechanical floor in this architecture (see R32).

General principle:
**A validator that proves a file was read proves nothing about whether that file's content actually changed what the session concluded. Wherever two of a project's own designated authorities can drift out of agreement (a manifest and its more authoritative pointer; a mandatory current-state file and a stale router), the fix is never a new parallel proof-of-diligence artifact — it is a narrow, purely structural agreement check between the specific authorities that are allowed to drift, sized to the actual demonstrated gap and no larger.**
